## Explanation of the Failure

When the verifier loads `value->task` from the map value at instruction 3:
```
3: (79) r1 = *(u64 *)(r0 +0)   R1=rcu_ptr_or_null_task_struct(id=10)
```

It correctly types this as `rcu_ptr_or_null_task_struct` — a pointer that **may be NULL** — because map values storing kptrs can always hold a NULL entry. `bpf_task_acquire` requires a **non-NULL** trusted pointer as its first argument. Since no NULL check is performed on `value->task` before the call, the verifier rejects it.

## Fix

Add an explicit NULL check on `value->task` before passing it to `bpf_task_acquire`. This narrows the type from `rcu_ptr_or_null_task_struct` to `rcu_ptr_task_struct` on the taken branch, satisfying the verifier.

```diff
 SEC("tp_btf/task_newtask")
 int BPF_PROG(entry, struct task_struct *task, u64 flags)
 {
 	struct task_struct *acquired;
 	struct map_value *value;
 
 	value = helper_a(task);
 	if (!value)
 		return 0;
 
+	if (!value->task)
+		return 0;
+
 	acquired = bpf_task_acquire(value->task);
 	if (!acquired)
 		return 0;
 
 	bpf_task_release(acquired);
 	return 0;
 }
```

After the `if (!value->task)` guard, the verifier knows `value->task` is non-NULL on the path that reaches `bpf_task_acquire`, eliminating the "Possibly NULL pointer passed to trusted R1" error.
