## Verifier Failure Analysis

The verifier is rejecting this program because the **combined stack size of nested function calls exceeds the limit of 512 bytes**.

Here's the call chain and stack usage:

1. `entry()` calls `helper_c()`
2. `helper_c()` allocates 260 bytes on stack, then calls `helper_b()`
3. `helper_b()` allocates 260 bytes on stack, then calls `helper_a()`
4. `helper_a()` allocates some stack space

The verifier tracks the maximum combined stack depth across all nested calls:
- `helper_c`: 260 bytes
- `helper_b`: 260 bytes  
- `helper_a`: 24 bytes (typical frame overhead)
- **Total: ~544 bytes** (exceeds 512-byte limit)

Additionally, `helper_c()` also calls `helper_d()` which allocates another 260 bytes, creating another deep call chain.

## Solution

The simplest fix is to **reduce `MAX_STACK` from 260 to a smaller value** that keeps the combined stack usage under 512 bytes. Given three nested functions each allocating `MAX_STACK` bytes, we need:

`3 * MAX_STACK + overhead < 512`

Setting `MAX_STACK = 128` gives us approximately `3 * 128 + 24 = 408 bytes`, which is safe.

## Patch

```c
#define MAX_STACK 128
```

**Why this works:** By reducing the per-function stack allocation from 260 to 128 bytes, the combined stack depth of nested calls drops from 544 bytes to approximately 408 bytes, which is well under the 512-byte verifier limit. This is the minimal change that addresses the root cause without restructuring the call graph.
