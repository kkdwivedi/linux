## Analysis

The verifier is failing due to exceeding the **liveness analysis complexity limit** (10001 calls). This happens because:

1. The program creates a deeply nested call chain: `entry` → `helper_a` (50 calls) → `helper_b` (50 calls) → ... → `helper_g` (50 calls)
2. This results in **50^7 = 78,125 billion** potential call paths to the innermost function `helper_g`
3. The verifier's liveness analysis must recompute which registers/stack locations are live across all these paths, causing exponential complexity
4. Each time `helper_g` is analyzed from different call contexts, the verifier re-analyzes it, hitting the 10,001 call limit

## Root Cause

The macro-based approach creates too many distinct call paths reaching the same subprogram. The verifier tracks liveness per call context, and with 50 calls at each of 7 levels, the number of distinct contexts explodes combinatorially.

## Solution

Reduce the nesting depth or the number of calls per level. The simplest fix is to **reduce `CALLS_50` to a smaller number** like `CALLS_10` or even fewer calls per level.

### Patch

```c
#define CALLS_10(fn) \
	CALL_AT(fn, 8) CALL_AT(fn, 16) CALL_AT(fn, 24) CALL_AT(fn, 32) CALL_AT(fn, 40) \
	CALL_AT(fn, 48) CALL_AT(fn, 56) CALL_AT(fn, 64) CALL_AT(fn, 72) CALL_AT(fn, 80)
#define CALLS_50(fn) CALLS_10(fn) CALLS_10(fn) CALLS_10(fn) CALLS_10(fn) CALLS_10(fn)
-#define CALLS_50(fn) CALLS_10(fn) CALLS_10(fn) CALLS_10(fn) CALLS_10(fn) CALLS_10(fn)
+#define CALLS_50(fn) CALLS_10(fn) CALLS_10(fn)
```

Or alternatively, reduce the depth by removing one or more helper levels (e.g., remove `helper_a` and have `entry` call `helper_b` directly).

**Why this works:** Reducing from 50 calls to 20 per level drops the call path explosion from 50^7 to 20^7, which is manageable by the verifier's liveness analysis within the 10,001 call limit.
