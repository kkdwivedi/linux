## Verifier Failure Explanation

The verifier is rejecting the program because of a **null pointer check failure** when accessing `s->x` in `helper_a()`.

Let's trace through the states:
- At instruction 7: `R1=mem_or_null(id=1,sz=4)` - this means R1 could be either valid memory OR null
- After `r6 = r1`: `R6=mem_or_null(id=1,sz=4)` - same type, still potentially null
- At instruction 10: `r2 = *(u32 *)(r6 +0)` - the verifier rejects this because R6 has type `mem_or_null`, not confirmed non-null memory

The root cause is that **BPF subprograms with pointer arguments must perform null checks before dereferencing**, even when the caller always passes a valid stack address. The verifier analyzes `helper_a()` independently and sees that `s` (in R1/R6) has type `mem_or_null` because the verifier conservatively marks pointer arguments to subprograms as potentially null.

The caller passes `&s` where `s` is a stack variable, which is always valid memory. However, the subprogram's standalone verification doesn't know this - it must defend against being called with NULL.

## The Fix

The smallest fix is to add a **null check** at the beginning of `helper_a()` before dereferencing `s`. This is standard practice for BPF subprograms with pointer arguments.

```patch
--- a/case.c
+++ b/case.c
@@ -9,6 +9,9 @@ struct Item {
 
 __noinline int helper_a(const struct Item *s)
 {
+	if (!s)
+		return 0;
+
 	return bpf_get_prandom_u32() < s->x;
 }
```

This satisfies the verifier because:
1. After the `if (!s) return 0;` check, the verifier refines R6's type from `mem_or_null` to just `mem` (confirmed non-null) on the fall-through path
2. The subsequent `s->x` dereference is then valid
3. The `return 0` for the null case provides a safe fallback

This is the idiomatic pattern for BPF subprograms that accept pointer arguments - always null-check before dereferencing, even if you believe the caller never passes NULL.
