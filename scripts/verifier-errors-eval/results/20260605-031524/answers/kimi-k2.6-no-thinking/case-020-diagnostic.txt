## Analysis of the Failure

The error is:
```
liveness analysis exceeded complexity limit (10001 calls)
```

The log shows `subprog#7 helper_g:` being analyzed at `depth 7` repeatedly, many times over. The suggestion says:
> Reduce the number of distinct call paths or argument patterns reaching these subprograms.

### Understanding the Program Structure

The program creates an extremely large call graph using nested macros:
- `CALLS_50(fn)` expands to 50 calls to `fn`
- `helper_g` is a leaf function (just returns 0)
- `helper_f` calls `helper_g` 50 times
- `helper_e` calls `helper_f` 50 times → 50×50 = 2,500 calls to `helper_g` at next level down
- This continues through `helper_d`, `helper_c`, `helper_b`, `helper_a`, and finally `entry`

The total call graph is enormous: 50^7 = 78,125,000,000,000,000 potential paths to `helper_g`.

However, the actual issue is **liveness analysis** - the verifier tracks which registers and stack slots are "live" (read before written) across function calls. When a subprogram can be reached via many different call paths with different liveness patterns, the verifier re-analyzes it multiple times.

### Why `helper_g` is Re-analyzed So Many Times

Each call to `helper_g` passes through `r1 = r10; r1 += -offset` - this sets up `r1` as a pointer to a different stack offset. Even though `helper_g` doesn't use `r1`, the **caller's liveness state differs** based on:
- Which call site in the parent (different stack offsets → different stack frame liveness)
- The depth of call stack and what registers are live at each level

The verifier caches subprogram analysis results, but the cache key includes the liveness state. With 50 call sites per function, each with different stack offsets, and 7 levels of nesting, the number of distinct liveness states reaching `helper_g` explodes.
