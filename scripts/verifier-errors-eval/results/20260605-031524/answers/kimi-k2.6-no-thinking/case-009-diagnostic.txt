## Verifier Failure Explanation

The error occurs at `case.c:42` where `bpf_task_acquire(value->task)` is called:

```
Possibly NULL pointer passed to trusted R1
```

The issue is that `value->task` is a `struct task_struct *` stored in a map value, and when loaded from the map, the verifier tracks it as `rcu_ptr_or_null_task_struct(id=10)` — meaning it could be NULL. The `bpf_task_acquire` kfunc requires a **non-NULL** trusted pointer.

Looking at the code flow:
1. `helper_a(task)` calls `map_insert(task)` which inserts a new entry with `local.task = NULL`
2. Then `map_insert` uses `bpf_kptr_xchg` to set `value->task = acquired` (a non-NULL acquired task)
3. On success, `map_insert` returns 0
4. Then `helper_a` calls `map_value_lookup(task)` which returns the map value
5. Back in `entry`, we do `bpf_task_acquire(value->task)`

The problem: **The verifier doesn't track that `value->task` was initialized to non-NULL through `bpf_kptr_xchg`**. From the verifier's perspective, when we load `value->task` from the map, it sees it as `rcu_ptr_or_null_task_struct` — it doesn't know that in this specific code path, the kptr was just initialized.

The root cause is in `map_insert()`: after `bpf_map_update_elem` with `local.task = NULL`, the map value's `task` field is NULL. The verifier tracks map values conservatively. Even though we then use `bpf_kptr_xchg` to set it to a non-NULL value, when we later look up the same map entry and read `value->task`, the verifier sees it as potentially NULL because:
- Map values can be accessed by other programs/CPUs
- The verifier doesn't preserve the precise state across `bpf_map_lookup_elem`

```c

	if (!value)
```

However, this changes semantics slightly. The real issue is that the verifier cannot prove `value->task` is non-NULL. But wait — in our specific code path, we **know** it's non-NULL because we just inserted it with `bpf_kptr_xchg`. The verifier's limitation is that it loses this information across map operations.
