The program is rejected before normal instruction verification starts:

```text
liveness analysis exceeded complexity limit (10001 calls)
processed 0 insns ...
```

This is not caused by an unsafe memory access. The verifier is blowing its liveness/call-chain analysis budget.

Each non-leaf function contains 50 static BPF-to-BPF calls to the next function:

```c
entry -> helper_a -> helper_b -> ... -> helper_g
```

There are 7 call levels, and each level has fan-out 50. Even though the program has only about 1k instructions, the verifier’s call/liveness walk sees a combinatorial number of call chains:

```text
50 + 50^2 + 50^3 + ... + 50^7
```

It hits the verifier’s internal liveness complexity limit at 10001 call visits, as shown by the repeated analysis of `helper_g`.

The smallest reliable source-level fix is to reduce the fan-out. With 7 levels, a uniform fan-out of 3 gives:

```text
3 + 3^2 + ... + 3^7 = 3279
```

which is below the 10001 limit. A fan-out of 4 would already be too high:

```text
4 + 4^2 + ... + 4^7 = 21844
```

So changing `CALLS_50()` to emit only 3 calls is a minimal safe edit.
