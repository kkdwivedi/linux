The program is rejected before normal instruction verification finishes because the verifier’s subprogram liveness walk blows up exponentially.

Each non-leaf function does 50 static BPF-to-BPF calls to the next helper, and the call chain is:

```text
entry -> helper_a -> helper_b -> helper_c -> helper_d -> helper_e -> helper_f -> helper_g
```

Because these are `static` subprograms, the verifier analyzes callees in caller context. With 50 call sites at each of 7 levels, the liveness analysis has to walk an enormous call tree. The log repeatedly shows:

```text
subprog#7: analyzing (depth 7)...
subprog#7 helper_g:
1064: r0 = 0
1065: exit
```

and eventually:

```text
liveness analysis exceeded complexity limit (10001 calls)
processed 0 insns ...
```

So this is not a semantic safety failure like invalid memory access; it is purely verifier complexity from the 50-way fanout.

A small source-level fix is to reduce the per-level fanout so the total liveness walk stays below the verifier’s 10k-call limit. With 3 calls per level, the expanded call tree is roughly:

```text
3 + 3^2 + 3^3 + 3^4 + 3^5 + 3^6 + 3^7 = 3279
```

which is comfortably below 10000.

```diff
--- a/test.c
+++ b/test.c
@@ -7,7 +7,7 @@
 	CALL_AT(fn, 8) CALL_AT(fn, 16) CALL_AT(fn, 24) CALL_AT(fn, 32) CALL_AT(fn, 40) \
 	CALL_AT(fn, 48) CALL_AT(fn, 56) CALL_AT(fn, 64) CALL_AT(fn, 72) CALL_AT(fn, 80)
-#define CALLS_50(fn) CALLS_10(fn) CALLS_10(fn) CALLS_10(fn) CALLS_10(fn) CALLS_10(fn)
+#define CALLS_50(fn) CALL_AT(fn, 8) CALL_AT(fn, 16) CALL_AT(fn, 24)
 
 __naked __noinline __used

```

The macro name becomes slightly misleading, but this is the smallest edit. If desired for clarity, rename it to `CALLS_3` and update the call sites, but functionally the one-line change should make the verifier pass by avoiding the liveness complexity limit.
