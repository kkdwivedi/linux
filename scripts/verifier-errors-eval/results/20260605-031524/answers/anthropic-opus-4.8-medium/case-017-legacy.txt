## Explanation

The `bpf_local_irq_save`/`bpf_local_irq_restore` API enforces **strict LIFO (nested) ordering** in the verifier, just like real IRQ save/restore semantics. Each `save` acquires a new "irq state" reference (id=1, then id=2), and the verifier requires that they be released in reverse order of acquisition.

In the source:
- `flags1` is saved first → id=1 (insn 3)
- `flags2` is saved second → id=2 (insn 7)

Then the code tries to restore `flags1` (id=1) first, but the verifier expects the most-recently-acquired state (id=2, `flags2`) to be restored first. Hence:

```
cannot restore irq state out of order, expected id=2 acquired at insn_idx=7
```

## Fix

Swap the two restore calls so they unwind in LIFO order:

```c
SEC("?tc")
int entry(struct __sk_buff *ctx)
{
	unsigned long flags1, flags2;

	bpf_local_irq_save(&flags1);
	bpf_local_irq_save(&flags2);
	bpf_local_irq_restore(&flags2);  /* restore most recent first */
	bpf_local_irq_restore(&flags1);
	return 0;
}
```

This matches the required nesting: `save(1) → save(2) → restore(2) → restore(1)`, satisfying the verifier's ordering check.
