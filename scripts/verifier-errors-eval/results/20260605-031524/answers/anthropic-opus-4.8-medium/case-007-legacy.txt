## What the verifier is complaining about

`slice_len` is a global (`.data`) variable. When you read it:

```
11: (61) r4 = *(u32 *)(r1 +0)   ; R4=scalar(... umax=0xffffffff ...)
```

the verifier only knows it is *some* `u32`, i.e. an unbounded value `[0, 0xffffffff]`.

`bpf_dynptr_slice(&ptr, 0, buffer, slice_len)` passes `buffer` (a fixed
`sizeof(struct ethhdr)`-byte stack slot) as the destination and `slice_len` as
the length. The helper's `ARG_PTR_TO_MEM` / size argument requires that the
length is bounded so the verifier can prove the copy into `buffer` stays within
the buffer. Because `slice_len` is unbounded, the verifier rejects it:

```
R4 unbounded memory access, use 'var &= const' or 'if (var < const)'
R3 and R4 memory, len pair leads to invalid memory access
```

## Smallest fix

Bound `slice_len` against the size of `buffer` before the call, exactly as the
verifier hint suggests (`if (var < const)`):

```c
	if (slice_len > sizeof(buffer))
		return SK_DROP;

	hdr = bpf_dynptr_slice(&ptr, 0, buffer, slice_len);
```

After this check the verifier knows `slice_len <= sizeof(buffer)`, so the
`(buffer, slice_len)` memory/length pair is provably within bounds and the call
verifies.

(Equivalently `slice_len &= sizeof(buffer) - 1;` would also bound it, but the
explicit `if (... > sizeof(buffer))` check is clearest and matches the helper's
required semantics.)
