## Explanation of the Verifier Failure

The BPF verifier's liveness analysis has a complexity limit of **10001 calls** (enforced to prevent unbounded exponential blowup). The program creates a call chain 8 levels deep:

> `entry` →(×50) `helper_a` →(×50) `helper_b` →(×50) `helper_c` →(×50) `helper_d` →(×50) `helper_e` →(×50) `helper_f` →(×50) `helper_g`

Because the verifier re-analyzes each subprogram for every distinct call context (it cannot fully cache liveness across all call sites), the total liveness analysis invocations grow as:

**N + N² + N³ + … + N^(D−1)** where N = 50 calls/level, D = 8 levels

This sums to roughly **50^7 ≈ 7.8 billion**, far exceeding 10001. The log confirms `helper_g` is entered at `depth 7` thousands of times before the limit is hit.

## Fix

The constraint to stay under 10001 is N^(D−1) < 10001. With D = 8 levels, we need N ≤ 3 (since 3^7 = 2187 < 10001, but 4^7 = 16384 > 10001).

The **smallest one-line fix** is to redefine `CALLS_50` to produce only 3 calls per level:

```diff
-#define CALLS_50(fn) CALLS_10(fn) CALLS_10(fn) CALLS_10(fn) CALLS_10(fn) CALLS_10(fn)
+#define CALLS_50(fn) CALL_AT(fn, 8) CALL_AT(fn, 16) CALL_AT(fn, 24)
```

With N = 3 and D = 8, total liveness calls ≈ 3 + 9 + 27 + 81 + 243 + 729 + 2187 = **3279**, safely under the 10001 limit.

The offsets 8, 16, 24 are already used by `CALLS_10`, so no other change is needed—stack frames remain valid and the structure (8 levels of nested calls) is preserved.
