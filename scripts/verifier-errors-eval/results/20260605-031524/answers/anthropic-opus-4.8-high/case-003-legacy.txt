## Root cause

The program spills the context pointer (`r1` = `ctx`) into the 8‑byte stack slot at `fp-8`:

```
*(u64*)(r10 - 8) = r1;     // fp-8 .. fp-1 now hold a spilled ctx pointer
```

Then it stores a single byte **inside that same 8‑byte slot**:

```
r0 = 0x23;
*(u8*)(r10 - 7) = r0;      // writes into byte fp-7, i.e. part of the spilled pointer
```

A spilled register is only tracked as a pointer while its whole 8‑byte slot is left untouched. Overwriting any byte of it invalidates the spill, so the verifier downgrades `fp-8` to a scalar (`fp-8=mmmmmmmm`). When the value is read back:

```
r0 = *(u64*)(r10 - 8);     // R0 = scalar(), not ctx
r0 = *(u64*)(r0 + 8);      // dereference of a scalar -> rejected
```

Hence:

```
R0 invalid mem access 'scalar'
```

This is exactly the verifier’s intended behavior: a partial write to a spilled pointer kills the pointer information.

## Fix

To make the program verify, don’t clobber the spilled pointer — put the byte store in a stack slot that does **not** overlap `fp-8 .. fp-1` (for example `fp-16`). That keeps `fp-8` a valid `ctx` spill, so the reload yields a pointer again.

Note that the final dereference also has to be a *legal* context access. A `u64` read at `ctx + 8` is not a valid `__sk_buff` access, so change it to a valid field/size (e.g. read `len` as `u32` at offset 0).

```c
SEC("socket")
__naked void entry(void)
{
	asm volatile ("					\
	*(u64*)(r10 - 8) = r1;				\
	r0 = 0x23;					\
	*(u8*)(r10 - 16) = r0;				\
	r0 = *(u64*)(r10 - 8);				\
	r0 = *(u32*)(r0 + 0);				\
	exit;						\
"	::: __clobber_all);
}
```

### Why this passes
- `*(u8*)(r10 - 16)` writes to a separate stack slot, leaving the 8‑byte spill at `fp-8` intact, so `r0 = *(u64*)(r10 - 8)` reloads a proper `ctx()` pointer instead of a scalar — eliminating the “invalid mem access 'scalar'” error.
- Reading `*(u32*)(r0 + 0)` is a valid `__sk_buff` context access, so the subsequent dereference is accepted.

The essential, minimal change is the first one (move the byte store off `fp-7` so it no longer overlaps the spilled pointer); the dereference adjustment is needed only because the original `u64` ctx read at offset 8 would not be a legal context access once the pointer is preserved.
