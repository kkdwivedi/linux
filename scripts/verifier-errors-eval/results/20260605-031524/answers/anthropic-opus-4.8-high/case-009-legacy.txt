## Explanation

The failure is at the very end of the log:

```
3: (79) r1 = *(u64 *)(r0 +0)   ; R1=rcu_ptr_or_null_task_struct(id=10)
4: (85) call bpf_task_acquire#63762
Possibly NULL pointer passed to trusted R1
```

In `BPF_PROG(entry, ...)` you do:

```c
acquired = bpf_task_acquire(value->task);
```

`value->task` is a kptr field loaded from the map value. When you load it, the verifier types it as `rcu_ptr_or_null_task_struct` — i.e. it **may be NULL**. `bpf_task_acquire()` is a `KF_TRUSTED_ARGS` kfunc and refuses a pointer that could be NULL, hence "Possibly NULL pointer passed to trusted R1".

Note that the `if (!value)` check earlier only guarantees that `value` (the map_value pointer) is non-NULL; it says nothing about the embedded `value->task` field, which was just stored as `NULL` during `map_insert` and only conditionally exchanged. So the verifier is correct that it can be NULL.

## Fix

Load the kptr into a local variable and null-check it before acquiring:

```c
SEC("tp_btf/task_newtask")
int BPF_PROG(entry, struct task_struct *task, u64 flags)
{
	struct task_struct *acquired, *kptr;
	struct map_value *value;

	value = helper_a(task);
	if (!value)
		return 0;

	kptr = value->task;
	if (!kptr)
		return 0;

	acquired = bpf_task_acquire(kptr);
	if (!acquired)
		return 0;

	bpf_task_release(acquired);
	return 0;
}
```

After `if (!kptr) return 0;`, the verifier narrows the type from `rcu_ptr_or_null_task_struct` to a non-NULL `rcu_ptr_task_struct`, which satisfies the trusted-arg requirement of `bpf_task_acquire()`, and verification proceeds.

This is the smallest source-level change: it adds the missing NULL check on the kptr field that the verifier was complaining about.
