## Explanation

`helper_a()` is a `__noinline` function, so the verifier treats it as a **global (BPF-to-BPF) function** and validates it independently from `entry()`. For such functions, a pointer-to-struct argument is passed in as type `PTR_TO_MEM_OR_NULL` (shown as `mem_or_null` in the log):

```
7: R1=mem_or_null(id=1,sz=4)
```

The verifier does not assume the caller passes a non-NULL pointer. It only knows the pointer *may* be NULL and *may* point to 4 bytes of memory. When the function then dereferences it without first checking for NULL:

```
10: (61) r2 = *(u32 *)(r6 +0)
R6 invalid mem access 'mem_or_null'
```

it rejects the access, because dereferencing a possibly-NULL pointer is unsafe.

## Fix

Add an explicit NULL check inside `helper_a()` before dereferencing `s`. After the check, the verifier narrows the type from `mem_or_null` to `mem`, making the load valid.

```c
__noinline int helper_a(const struct Item *s)
{
	if (!s)
		return 0;
	return bpf_get_prandom_u32() < s->x;
}
```

This is the smallest source-level change: the `if (!s)` branch lets the verifier prune the NULL case, so on the path reaching `s->x` the register is a valid `PTR_TO_MEM` of size 4, and the 4-byte load at offset 0 is accepted.

(Equivalently, one could annotate the argument as non-null with the `__arg_nonnull` tag, e.g. `helper_a(const struct Item *s __arg_nonnull)`, but the explicit NULL check is the simplest and most portable fix.)
