## Explanation

The failure is at `entry` line 42:

```c
acquired = bpf_task_acquire(value->task);
```

`value->task` is a kernel pointer (kptr) stored in the map. When the verifier loads it:

```
3: (79) r1 = *(u64 *)(r0 +0)   ; R1=rcu_ptr_or_null_task_struct(id=10)
```

it gets type `rcu_ptr_or_null_task_struct` — a pointer that **may be NULL**. The kfunc `bpf_task_acquire()` requires a *non-NULL* trusted/rcu pointer, so the verifier rejects the call:

```
Possibly NULL pointer passed to trusted R1
```

Note the `NULL` check earlier (`if (r0 == 0)`) only guards the *map value pointer* `value`, not the embedded kptr `value->task`. The kptr itself can legitimately be NULL (it was even initialized to NULL in `map_insert`), so the verifier insists on an explicit NULL test before passing it to the kfunc.

## Fix

Load the kptr into a local, NULL-check it, and only call `bpf_task_acquire()` on the non-NULL path. The verifier's own suggestion is exactly this.

```c
SEC("tp_btf/task_newtask")
int BPF_PROG(entry, struct task_struct *task, u64 flags)
{
	struct task_struct *acquired, *kptr;
	struct map_value *value;

	value = helper_a(task);
	if (!value)
		return 0;

	kptr = value->task;
	if (!kptr)
		return 0;

	acquired = bpf_task_acquire(kptr);
	if (!acquired)
		return 0;

	bpf_task_release(acquired);
	return 0;
}
```

After the explicit `if (!kptr) return 0;`, on the fall-through path the register's type is narrowed from `rcu_ptr_or_null_task_struct` to a non-NULL `rcu_ptr_task_struct`, which satisfies `bpf_task_acquire()`'s contract and lets verification pass.

(The original `if (!acquired)` check remains correct and necessary for the kfunc's *return* value, but it does not help the *argument*, which is what this patch addresses.)
